Los makefiles aceptan reglas de patrón, variables automáticas y variables para generalizar y simplificar el proceso de compilación.

Generalizando los makefiles

Reglas de patrón y variables automáticas

  • % en una regla de patrón casa con cualquier raíz: %.o: %.cpp sirve para main.o, auxiliar.o…
  • $@ representa al objetivo actual.
  • $< representa el primer prerrequisito.
  • $^ representa la lista completa de prerrequisitos.

Generalizando los makefiles

ejecutable: main.o auxiliar.o
    g++ -o $@ $^

%.o: %.cpp
    g++ -c $< -o $@ -I.

Tip

Para compilar usa $<, no $^: si más adelante añades cabeceras como prerrequisitos, $^ se las pasaría también al compilador.

Generalizando los makefiles

También se pueden definir variables que usamos en el fichero

CXX      := g++
CXXFLAGS := -Wall -std=c++20
CPPFLAGS := -I.
LDLIBS   := -l<libreria>
OBJECTS  := main.o auxiliar.o

ejecutable: $(OBJECTS)
    $(CXX) $(LDFLAGS) -o $@ $^ $(LDLIBS)

%.o: %.cpp
    $(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@

Generalizando los makefiles

Variables: algunas convenciones

  • Nombres estándar: CXX (compilador C++), CXXFLAGS (opciones de compilación), CPPFLAGS (preprocesador, -I), LDFLAGS (enlazador, -L), LDLIBS (librerías, -l).
  • Se pueden sobrescribir desde la línea de comandos: make CXXFLAGS=-O2.
  • := evalúa el valor en el momento de la asignación; = lo evalúa cada vez que se usa. Por defecto, usa :=.

Las convenciones de nombres son las que usan las reglas implícitas de make y las que reutilizaremos con ccache (make CXX="ccache g++").

make tiene funciones y utilidades para trabajar con cadenas de caracteres.

Se invocan como $(func arg1,arg2,...)

Advertencia

Las funciones en los makefiles son sensibles a los espacios: al trabajar con cadenas, $(func arg1,arg2) no devuelve el mismo resultado que $(func arg1, arg2) (el segundo argumento empieza por un espacio).

Ejemplos de funciones

  • wildcard: equivalente a usar * y ? en el terminal.
  • info: imprime un mensaje (lo evalúa make, no el terminal).
  • subst: reemplazo literal de cadenas.
  • patsubst: reemplazo de cadenas por patrones.
  • addprefix: añade un prefijo a cada elemento de una lista.
  • shell: ejecuta un comando del terminal y devuelve su salida.

Funciones en la práctica

SOURCES := $(wildcard *.cpp)
OBJECTS := $(patsubst %.cpp,%.o,$(SOURCES))

ejecutable: $(OBJECTS)
    $(CXX) $(LDFLAGS) -o $@ $^ $(LDLIBS)

%.o: %.cpp
    $(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@

Forma abreviada equivalente: $(SOURCES:.cpp=.o). Evitamos subst aquí porque reemplaza cualquier aparición de “.cpp” dentro del nombre, no solo la extensión.

Advertencia

Recuerda que, para que se ejecuten info o clean, debes indicarlo al llamar a make: make clean.

¿Qué pasa si en el directorio existe un fichero llamado clean?

make responde “‘clean’ is up to date” y no borra nada: el fichero existe y no tiene prerrequisitos. Diferencia entre ambos objetivos: info usa una función de make; clean lanza comandos de shell.

Objetivos sin fichero

Los objetivos que no generan un fichero se declaran en el objetivo especial .PHONY.

.PHONY: all clean info

all: ejecutable

Advertencia

.PHONY es un objetivo, no una variable: .PHONY := clean no tiene ningún efecto.

Objetivos estándar

En un proyecto software se esperan, al menos, los siguientes objetivos:

  • all: será el primero y representa el objetivo por defecto.
  • clean: borra todos los ficheros intermedios que se puedan volver a generar al ejecutar make.
  • dist: crea un fichero que contiene la distribución del proyecto.
  • install: instala el resultado de crear el proyecto.
  • uninstall: desinstala el resultado de crear el proyecto.
  • check (o test): ejecuta las pruebas.

Dependencias automáticas

El compilador puede generar las dependencias por nosotros.

CPPFLAGS += -MMD -MP
DEPS     := $(OBJECTS:.o=.d)

-include $(DEPS)
  • -MMD: al compilar main.cpp genera main.d con las cabeceras del proyecto que incluye.
  • -MP: añade una regla vacía por cabecera, para que borrar un .h no rompa la compilación.
  • -include: incluye los .d si existen (la primera vez no existen y no pasa nada).

Ejecución paralela

  • make puede lanzar compilaciones en paralelo.
  • Para ello se usa la opción -j seguida del número de trabajos: make -j4 o make -j$(nproc).
  • Lanzar trabajos en paralelo suele descubrir dependencias mal especificadas: no es lo mismo satisfacerlas de forma secuencial que en paralelo.

Depurar un Makefile

  • make -n: muestra los comandos que ejecutaría, sin ejecutarlos.
  • make -B: fuerza a rehacer todos los objetivos.
  • make -C dir: ejecuta make dentro de dir.
  • make -p: muestra la base de datos de reglas y variables (incluidas las implícitas).

Estrategia monolítica

Debemos descubrir los ficheros fuente y generar sus .o correspondientes

BUILD    := build
# Directorios con código fuente
SRC_DIRS := src lib
SRCS     := $(shell find $(SRC_DIRS) -type f -name '*.cpp')
OBJS     := $(patsubst %.cpp,$(BUILD)/%.o,$(SRCS))
DEPS     := $(OBJS:.o=.d)

Advertencia

No pongas comentarios al final de una asignación: SRC_DIR := src #comentario guarda "src ", con el espacio final, y las rutas $(SRC_DIR)/... dejan de funcionar.

Estrategia monolítica

También hay que indicar dónde están las cabeceras

BUILD    := build
# Directorios con código fuente
SRC_DIRS := src lib
SRCS     := $(shell find $(SRC_DIRS) -type f -name '*.cpp')
OBJS     := $(patsubst %.cpp,$(BUILD)/%.o,$(SRCS))
DEPS     := $(OBJS:.o=.d)
INC_DIRS := include
CPPFLAGS := $(addprefix -I,$(INC_DIRS)) -MMD -MP

Estrategia monolítica

Aplicación en compilación

.PHONY: all clean
all: $(BUILD)/game

$(BUILD)/game: $(OBJS)
    $(CXX) $(LDFLAGS) $^ -o $@ $(LDLIBS)

$(BUILD)/%.o: %.cpp
    @mkdir -p $(@D)
    $(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@

clean:
    rm -rf $(BUILD)

-include $(DEPS)

$(@D) es el directorio del objetivo (build/src, build/lib). Aquí no usamos dependencia de orden porque cada objeto puede ir a un directorio distinto. La @ delante de un comando evita que make lo imprima.

Estrategia monolítica

Ventajas:

  • Simple: mantienes un solo Makefile por proyecto.
  • make conoce el grafo de dependencias completo.
  • Paralelizable: make -j respeta todas las dependencias.

Inconvenientes:

  • El fichero crece con el proyecto y es más difícil de mantener.

Estrategia recursiva

Código del Makefile coordinador

SUBDIRS := lib src
export BUILD := $(CURDIR)/build

.PHONY: all $(SUBDIRS)

all: $(SUBDIRS)
    @echo "Proyecto compilado correctamente"

# src necesita la librería de lib
src: lib

$(SUBDIRS):
    $(MAKE) -C $@ --no-print-directory
  • $(MAKE) en lugar de make: propaga opciones como -j a los sub-make.
  • export pasa la variable a los sub-make.
  • $(CURDIR) hace la ruta absoluta: -C cambia de directorio y una ruta relativa apuntaría a src/build.
  • src: lib hay que declararlo a mano; sin ello, make -j puede compilar src antes que lib.

LIB  := $(BUILD)/lib/libmathx.a

.PHONY: all

Estrategia recursiva

Código del Makefile de src

BIN       := $(BUILD)/game
LIBSTATIC := $(BUILD)/lib/libmathx.a
SRCS      := $(wildcard *.cpp)
OBJS      := $(patsubst %.cpp,$(BUILD)/src/%.o,$(SRCS))

.PHONY: all
all: $(BIN)

$(BIN): $(OBJS) $(LIBSTATIC)
    $(CXX) $(LDFLAGS) $^ -o $@ $(LDLIBS)

$(BUILD)/src/%.o: %.cpp | $(BUILD)/src
    $(CXX) $(CXXFLAGS) -I../include -c $< -o $@

$(BUILD)/src:
    mkdir -p $@

¿Qué pasa si ejecuto make dentro de src/ sin haber compilado lib/?

Falla con “No rule to make target …/libmathx.a”: el make de src no sabe construir la librería. Es justo el problema que plantea Peter Miller en la siguiente diapositiva.

Estrategia recursiva

Ventajas:

  • Makefile más sencillos y mayor limpieza visual.
  • Coordinación del proyecto a través de un makefile global.
  • Permite compilaciones parciales para testear módulos.

Inconvenientes:

  • Cada make solo ve su parte del grafo de dependencias.
  • Las dependencias entre módulos (src: lib) se mantienen a mano.

¿La recursividad es buena?

Tema polémico en la comunidad C/C++:

  • Peter Miller (1997): Recursive Make Considered Harmful. Los make recursivos fragmentan el árbol de dependencias y eso lleva a builds incoherentes, largos tiempos de espera o necesidad de hacer make clean con frecuencia.

¿La recursividad es buena?

Tema polémico en la comunidad C/C++:

  • En StackOverflow también hay debate:

Recursive makefiles are bad primarily because you partition your dependency tree into several trees. This prevents dependencies between make instances from being expressed correctly.

¿La recursividad es buena?

Tema polémico en la comunidad C/C++:

Los sistemas de proyectos autoconfigurables como CMake, Meson o Premake han ganado popularidad porque abordan estos problemas: permiten gestionar dependencias completas sin renunciar a modularidad y escalabilidad.

¿La herramienta make es exclusiva de C y C++?

No: sirve para cualquier proceso “ficheros que generan ficheros”: documentos LaTeX, estas mismas transparencias, conversión de imágenes, pipelines de datos…

Si el resultado va a ser el mismo, devolver el resultado ya obtenido.

Ccache

Compiler Cache (ccache) es una herramienta que nos permite realizar esto.

Se utiliza como una herramienta complementaria al compilador.

ccache g++ -c main.cpp -o main.o

Advertencia

ccache solo cachea la compilación (-c). El enlazado no se cachea.

Características

  • Soporta C, C++, Objective-C, Objective-C++ y CUDA, con GCC, Clang, MSVC y NVCC.
  • Mantiene estadísticas de aciertos/fallos.
  • Tamaño máximo configurable (ccache -M 10G) y limpieza automática.
  • Puede cachear compilaciones con warnings (y los vuelve a mostrar).
  • Añade una sobrecarga mínima al proceso de compilación.
  • Comprime la caché con Zstandard, activado por defecto desde la versión 4.0.

Uso de ccache

Se puede usar como prefijo.

ccache g++ -c main.cpp -o main.o

Gracias a las variables convencionales, se integra directamente con make:

make CXX="ccache g++"

Uso de ccache

O suplantando al compilador mediante enlaces simbólicos con su nombre:

# Debian/Ubuntu ya incluyen estos enlaces
export PATH="/usr/lib/ccache:$PATH"

# A mano
sudo ln -s $(which ccache) /usr/local/bin/g++
sudo ln -s $(which ccache) /usr/local/bin/gcc

ccache detecta con qué nombre se le ha llamado y busca el compilador real más adelante en el PATH.

Cómo funciona ccache

ccache calcula un hash con la información que determina el resultado de la compilación

Si encuentra un hash idéntico en su registro (hit): devuelve el resultado sin compilar.

Si no encuentra nada (miss): compila y guarda el resultado.

Modos de ccache

ccache soporta tres modos:

  • Directo (por defecto): el hash se calcula a partir del fuente y sus cabeceras, sin ejecutar el preprocesador. Si falla, recurre al modo preprocesador.
  • Preprocesador: el hash se calcula sobre la salida del preprocesador.
  • Dependencias (opcional): nunca ejecuta el preprocesador; usa la información de dependencias que genera el compilador (-MD).

Modos de ccache

ccache soporta tres modos:

  • Directo: muy rápido, pero cualquier cambio en el texto del fichero es un miss.
  • Preprocesador: robusto, pero más lento (hay que preprocesar siempre).
  • Dependencias: rápido, pero exige compilar con generación de dependencias.

Modos de ccache

¿Y si solo cambio un comentario?

  • Modo directo: miss, el contenido del fichero ha cambiado.
  • Modo preprocesador: el preprocesador elimina los comentarios, así que puede haber hit… siempre que no cambien los números de línea.

Ninja

⏱ 1:45 – 1:50 (5 min). Solo mención: no se practica a mano; lo verán generado por CMake en el Tema 6.

¿Qué es Ninja?

Ninja es un sistema de construcción minimalista enfocado en la velocidad.

  • Ocupa el mismo lugar que make (capa 1).
  • Do less, but do it quick: sin funciones, sin condicionales, sin reglas implícitas.
  • Paraleliza por defecto.
  • Sus ficheros build.ninja están pensados para que los genere otra herramienta (CMake, Meson…).

Aspecto de un build.ninja

cxxflags = -O2 -Wall

rule cxx
  command = g++ $cxxflags -c $in -o $out

rule link
  command = g++ $in -o $out

build main.o: cxx main.cpp
build app: link main.o
default app
  • rule ≈ receta; build salida: regla entradas ≈ regla de make.
  • $in y $out ≈ $^ y $@.

¿Merece la pena escribir Ninja a mano?

Según su documentación…

Make’s language was designed to be written by humans. Many projects find make alone adequate for their build problems. In contrast, Ninja has almost no features; just those necessary to get builds correct while punting most complexity to generation of the ninja input files.

¿Merece la pena escribir Ninja a mano?

Según su documentación…

Ninja by itself is unlikely to be useful for most projects.

Tip

Esto no significa que Ninja sea inútil: es raro usarlo por sí solo. Lo veremos en el Tema 6 como backend de CMake (cmake -G Ninja).
